## 0. 这一份是干什么的

`CONTAINER.md` §5 把选择摆成互斥的两条：

- **(a) 容器是文档**——论文数字保持 Windows 产出，容器供读者复跑；
- **(b) 容器是准绳**——在容器里重跑，**用容器的数字作为论文的数字**。

**作者已选 (b)（2026-09-07）。**

(b) 更相称于一篇以复现审计为核心的论文，但它有真实代价：
**任何一个数动了，论文就得改，而已经读过前一版的评审会看到一份不同的稿子。**
本文件在构建镜像之前把这件事的规则写死，**代价是事先接受的**。

⚠ 本项目纪律 §五-56：§7 是事前预期，写在看任何重算结果之前。

## 1. 为什么必须事前写

论文当前的数产自 **Windows 11 / x86_64-w64-mingw32 / R 参考 BLAS /
`Chinese (Simplified)_China.utf8` 且 `LC_NUMERIC=C`**（`150b_session.txt`）。
容器是 **Linux / OpenBLAS / `C.UTF-8`**。

已知会造成差异的来源，事前列明，**不是事后用来解释某个不合意的数**：

1. **浮点**：BLAS、编译器、libm 实现不同，末位可变；
2. **排序**：locale 不同 → 按字符键排序再取第一行的步骤可能取到别的行；
3. **包解析**：`150a_environment.lock` 锁版本，但 Bioconductor/Posit 快照的
   依赖解析仍可能不同；
4. **Python 补丁版本**：记录为 3.12.4，容器给的是发行版的 3.12.x；
5. **外部二进制**：SMR / PLINK 的 Linux 构建与 Windows 构建。

⚠ **随机性不在此列**：R 与 numpy 的种子化 RNG 跨平台确定。
若种子化结果仍变，那是 **1–3 之一在起作用**，不得记为"随机波动"。

## 2. 接受判据（两层，跑前定死）

### 层一：正文引用的每一个数

判据 = **在正文印出的精度上四舍五入后相同**。
正文印 `4.96`，容器就必须在两位小数上给出 `4.96`。

**执行方式**：容器内重跑分析步骤 → 重跑
`step127_audit_manuscript_numbers.py`。它逐个把正文的数与表对账，
**任何一个 `MISSING` 就是一个动了的数**。同理跑 `step153` / `step154` / `step155`。

⚠ 这正是 `step127` 存在的理由，本文件不另造判据。

### 层二：每一个**判定**（categorical）

以下必须逐字相同，**层二的翻转比层一的位移严重得多**：

- 每个格子的显著/不显著、阴性对照通过/失效、cell void 与否；
- `147a_finemap_decomposition.tsv` 的 `seed_stable`（T/F）与 `verdict`；
- `101b_matched.tsv` 的 `criterion_met`；
- `130c_multilist_verdict.tsv` 的判定列；
- `cqtna` 包 `testthat` 的 271 项断言全过；
- `step101` 自带的 PC（"重现 85.8% / 22.8%"）必须仍然通过。

## 4. ⚠ 全有或全无条款（本文件最要害的一条）

**不得**在容器与 Windows 之间挑选：
一致处采用容器值、不一致处保留 Windows 值——**这是选择性报告**。

只有两种合法终局：

- **容器成为准绳**：所有**可重跑**的数一律采用容器值，
  连同任何翻转了的判定一起采用并报告；
- **容器不作准绳**：全部退回 (a)，`CONTAINER.md` §5 改回 (a) 的措辞，
  并在正文写明退回的理由。

## 5. 数字动了怎么办（迁移规则）

1. 在 `manuscript/NUMBER_MIGRATION_fixed_anchor.md` 里登记：旧值、新值、来源表、步骤；
2. 正文、补充材料、**图注**、`step127` 期望值一并改；
   ⚠ 图注里的数字 `step154` **查不到**，必须手工核（`step127` §1a–1d 才查数）；
3. 重跑四个审计直到全绿；
4. 在 §9 逐条列出**每一个**动过的数——**不得只报"多数一致"**。

## 6. 判定翻转怎么办

**按"翻了"报告，不得静默采用。**

1. 在正文新增或扩写一句，说明该判定在两个环境下不同；
2. 在 §9 记录两个环境各自的值与差异来源（若可判定）；
3. ⚠ **若翻转发生在 `seed_stable` 上**：那不是构建问题，
   而是**关于方法的结果**——S45 的结论应据此加强，
   即该量既依赖种子也依赖环境。

## 7. 事前预期（写在跑之前）

- **绝大多数数不会在正文印出的精度上变**。倍数、计数、两位有效数字的 P 值应当稳定。
- **最可能动的是 `step147`**（susie 纯度按 100 个变异随机抽样估计，
  S45 已记录无种子时 0/1/0 的行为）。**我预期 `seed_stable` 至少有一格翻转。**
- **计数类（位点数、记录数、基因数）应当完全相同**；若不同，
  优先怀疑 §1 第 2 条（locale 排序），而不是浮点。
- **`step101` 的 PC 我预期仍然通过**；若不过，说明浮点差异已大到影响下采样重现，
  那本身是重要发现。
- **`step151` / `step156` / `step158` 应当完全不动**（纯文本、纯列联）。

⚠ **若结果与上述相反**——例如 `step147` 稳定而计数类反而变了——
必须在 §9 写明"§7 未预见"，**不得**事后编一个机制。

## 8. 停止规则与作废条件

- **镜像构建失败或依赖解析与 `150a` 不符** → 记录差异，**先修镜像**，不得带伤重跑；
- **必跑清单第 1–2 项就失败**（审计红或包测试挂） → 判为环境未就绪，
  **不得**继续跑 3–7 并解释单个数字；
- **可重跑覆盖率低于正文所引数字的一半** → 容器不足以作准绳，**退回 (a)**，
  按 §4 的第二种终局处理；
- 重跑只做一次。不得在看到结果后更换镜像基底、包快照或容差。

#### 9.8.1 事实

#### 9.8.2 成因：不是浮点，是一条没有唯一解的规则

按 §1 的要求定位到具体成因，**不得记为"随机波动"**：

`step85e` 的设计写明"每个位点由其 **lead record = 最小 exposure eQTL p** 代表"。
但在 eQTLGen 的输入里：

- `pval_exp` 的最小值是 **3.2717×10⁻³¹⁰**（一个**次正规数**，
  说明真实 P 值已下溢、被压到同一个可表示的底）；
- **12,835 行中有 2,349 行（18.3%）并列在这个值上**；
- 另有 426 个并列组内 `eaf` 不唯一。

代码为 `d.sort_values("pval_exp")` 后 `.agg(eaf=("eaf","first"))`——
`sort_values` 默认 **quicksort，不稳定排序**。
**对 18.3% 的数据，"最小 p" 选不出唯一的行**，取到谁由排序实现决定；
换 numpy 版本，排序后的行序完全不同（已实测：两环境下排序后
`eaf` 序列的 md5 不同，前 8 行即全部相异）。
lead 变 → 该位点 EAF 变 → 落入的 EAF 五分位变 → 匹配层变 → 期望值变。

⚠ **已排除 RNG 为成因**：`default_rng(85)` 在 numpy 2.0.0 与 2.5.2 下
给出**完全相同**的抽样序列（实测 10 次抽样逐位相同）。

**波及范围**：melanoma、HCC_high、HCC_low 的最小 p 仅各有 2 行并列（0.1%），
故本次未被触发——但 HCC 两个数据集**各有 1 个并列组 `eaf` 不唯一**，
**同样暴露在这个机制下**，只是这次没翻。
`step127` 对账的 melanoma 值 6.66 本次未变。

#### 9.8.3 这意味着什么

1. **这不是容器的缺陷，也不是 Windows 的缺陷。**
   容器跑的恰恰是 `requirements.txt` 所钉、
   注释称"论文 Software 节所记录"的 numpy 2.0.0；
   而作者机已漂移到 2.5.2。
2. **正文那个 6.49，当前无法从存档中重现**——
   两个环境给出两个别的数。
3. ⚠ **这是一个方法层面的问题，不是环境层面的问题。**
   "最小 p 作 lead"这条规则对 18.3% 的数据没有唯一解，
   6.489 / 6.057 / 6.870 **三者都是任意的**，
   区别只在于是哪一次不稳定排序的产物。
   **不得**从三者中挑一个采用——那正是 §4 禁止的选择性报告。

### 10.3 2026-09-11：第 7 组第二次扩大，以及 102 个脚本的路径修改
⚠⚠ **两件事都发生在结果已被观察之后，第二件还修改了分析脚本本身。这一行必须先读。**

**发现者**：第三方评审指出 §9.6「41/41 = 100%」的分母有误。
执行者据此新写 `step161` 度量真正的 C/A，得 **82/191 = 42.9%**，低于 §8 的 50% 退回线。

#### 缺陷一：第 7 组的实现仍然窄于 §3 的措辞（与 §10.2 同源）

§3 第 7 组写的是「其余输入齐备的 `step*`」，而实现是 `step1[2-5][0-9]`，
即**编号 120 以下的 118 个脚本从未被尝试过**——这不等于它们不能在这里跑。
改为全仓库 `step*`。

**⚠ 扩大之后覆盖率一个数都没动**，仍是 82/191。原因是缺陷二。

#### 缺陷二：102 个脚本写死了作者机的路径

**158 个 `step*` 脚本中有 102 个写着 `MR = r"D:/R_ex/MR"` 且无任何覆盖。**
在容器内它们**败在路径上，不是败在数据上**。按编号：

| 区间 | 可移植 | 写死 |
|---|---:|---:|
| 6–99 | 16 | 79 |
| 100–119 | 1 | 20 |
| 120–161 | 39 | 3 |

**旧 glob `step1[2-5][0-9]` 几乎恰好描出了这条可移植性边界。**
它不是随意收窄的，它一直在跟踪「哪些脚本能在任何地方跑」——
所以那个覆盖率数字报告的是脚本碰巧可移植的比例，**不是容器能重算什么**。

⚠ **HANDOFF v13 §1 据以提出 97/191 = 50.8% 的三个脚本
（`step53`/`step55`/`step104`）正在这 102 个之内**，本次运行中三者全部败于
`D:/R_ex/MR/13_meta_locus_annotation.tsv`。**那三次「跑通」是在 Windows 上跑的。**
把它们计入容器重算，与 §9.6 更正框指出的「把已审计当成已重算」是同一类替换，**第三次**。

#### 作者裁定与修改范围

**作者于 2026-09-11 授权**：修改路径解析后重跑，按重跑结果裁定 §8。

102 个文件，**只改路径解析**，形如

```python
MR = (sys.argv[1] if len(sys.argv) > 1
      else os.environ.get("CQTNA_DIR") or r"D:/R_ex/MR")
```

R 用 `commandArgs`/`Sys.getenv` 等价写法。**每个文件的默认值一字未改**，
故在作者机上不带参数运行的行为与此前相同。

⚠ **为什么这不同于 §8 禁止的事，以及它比 §10.2 走得更远。**
§8 禁止「看到结果后更换**镜像基底、包快照或容差**」——三者一个未动。
但 §10.2 只是**扩大了被执行的范围**（结构上无法把结果引向「一致」），
**本条修改了分析脚本**，那个理由在这里不成立。
其正当性只来自两点，缺一不可：

1. 改动限于路径解析、默认值不变，且该限制**经机械检查**而非仅凭声明；
2. 由作者在看到 42.9% 与 §8 后果之后**明示授权**，与 §9.8 修 `step85e` 同规格。

**如实登记，不假装是事前设计。**

#### ⚠ 那个机械检查本身是不够的——它验错了东西

对 `git diff -U0` 的检查只放行三种行（删除旧赋值、加入新解析、补 `import`），
报告 **99 个文件、0 行落在三种之外**。执行者把这个结果当成了「已验证」。

**它验的是被改行的形状，完全没有验 `argv[1]` 原本是不是已经有别的含义。**
而有两个脚本恰恰如此：

- `step91_literature_audit.py`：`src = sys.argv[1]`，是 PMID 清单的路径；
- `step21_spatial_LR_coloc.py`：`argv[1]` 是配体-受体表，`argv[2]` 是标签。

两者都会**静默地把一个文件名当成仓库目录**。
⚠ 执行者随后的第一次手工排查**又漏掉了 `step21`**，因为它那行
`LR_FILE = sys.argv[1] if len(sys.argv) > 1` 含有过滤条件里用来排除 MR 行的同一段子串。

**修法不是再查一遍，而是把检查搬到做出该假设的地方**：
`step159` 新增 `argv_guard()`，在跑第 7 组之前报出任何**复用了自己取 MR 的那个下标**
的脚本。已用一个构造出来的冲突（被报出）与其修正版（未被报出）验证，
在仓库上干净。`step91`/`step21` 改用 `argv[2]`/`argv[3]`，
即 `step157`/`step158` 早已在用的约定。

#### 缺陷三：`step161` 自身两处系统性低估
